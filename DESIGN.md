# Khata: how it works

Khata takes a week of exported WhatsApp chats from a kirana shop (the text plus the bill photos,
rate-list PDFs, UPI screenshots, statements and voice notes), keeps a record of what every
distributor has agreed to, and reports bills that are costing the shop money. Each finding comes
with the amount, the chat line or bill row that proves it, how sure we are, and what it's safe to
do about it.

There are three commands and each one runs on its own: `ingest` reads a week of chats, `report`
writes the findings for a given date, and `feedback` takes the owner's answers. Nothing stays in
memory between them; everything lives in the `--state-dir` folder.

```
 week folder (_chat.txt + attachments)                state folder
        |                                               distributors/<CODE>.json   what each distributor sent and agreed
        v                                               shop.json                  who the owner is, who's who
   ingest: parse chat, screen for scams,       ---->    feedback.json              the owner's answers
   work out who is who, read attachments,               alerts.json                quarantined messages
   turn messages into dated records                     cache/                     saved model answers

   report --as-of DATE: look only at what had arrived by DATE, run the six checks,
   apply the owner's feedback, decide actions, write report.json
```

## Where we started

We began with a version generated by Gemini. Going through it, we found a few serious problems:

- **None of the media was real.** Every bill photo, PDF and voice note in `data/` was a 16-byte
  placeholder (literally the text `dummy_image_data`). The results all came from hand-written
  `.json` files sitting next to them. Take those away and it found nothing at all. We wrote real
  readers for photos, PDFs and audio and generated proper test media. The `.json` files are now only
  an optional saved reading.
- **Distributor names were hard-coded** ("GANGA" or "RAMESH" means GT, and so on). A new shop,
  which is exactly what the hidden test uses, wouldn't have been recognised. Now we work it out
  from the chat itself.
- **The bundled grader gave most points away** (full feedback marks for any report, for example).
  We wrote a stricter one and our own test shop with an answer key.
- Smaller things: it asked GST questions about bills that charged no GST, it threw away any bill
  with suspicious text on it (so an attacker could hide a bill that way), its scam filter blocked
  normal phrases like "account number", and it ignored rate lists that didn't print an effective date.

We kept the overall layout, the per-distributor JSON files, the "use the rate that was valid on
the bill date" idea, and the split into six checks.

## Meta models

All model calls go to the Meta Model API (`https://api.meta.ai/v1`), through the standard
OpenAI-compatible client.

- **Muse Spark 1.3, vision:** reads bill photos, UPI screenshots, statements and scanned PDFs.
  We check its reading against the bill's own arithmetic (quantity × rate should equal the amount,
  rows should add up to the subtotal, and so on). If it doesn't add up, we rotate the photo and try
  again, which handles sideways photos. If the bill has instructions printed on it, we note them and
  ignore them.
- **Muse Spark 1.3, text:** reads chat messages and voice transcripts in Hinglish and Devanagari,
  PDFs our table reader can't handle, maps bill item names to rate-list names, double-checks
  suspicious forwarded messages, and reads the owner's free-text feedback. Any number it returns
  has to be in the original text, and it can't call a scheme "permanent" unless the message actually
  says so.
- **Muse Voice Transcribe 1.0:** voice notes. WhatsApp's `.opus` audio is converted to 16 kHz WAV
  and uploaded to `/v1/asr/transcribe`, as in Meta's cookbook. If that isn't available we fall back
  to Whisper running locally.

We set Muse Spark's `reasoning_effort` to `low`. Reading a bill isn't hard, and its reasoning tokens
count against the output limit, so this keeps long bills from being cut off and saves credit too.
Model answers are saved by file content, so re-running the same files costs nothing.

The endpoint and model names are just settings, so the same code runs on open Llama weights from
any OpenAI-compatible host (the problem statement allows "any host, or locally").

## Reading a week of chats

**The chat file.** We handle both the iPhone export (`[dd/mm/yy, hh:mm:ss] Name: ...`,
`<attached: ...>`) and the Android one (`dd/mm/yyyy, h:mm am - Name: ...`,
`IMG-...jpg (file attached)`), 12 and 24 hour times, the invisible characters WhatsApp adds,
multi-line messages, and forwarded markers. We figure out day/month order from the whole file. Any
`.txt` that looks like a chat is used, so a folder with one export per distributor also works.

**Who's who.** We score each sender to find the owner: people address them by the shop's name
("Namaste Laxmi Stores ji"), they send UPI screenshots and place orders, and they don't send bills.
A name like "Ramesh Ganga Traders" splits into the person (Ramesh) and the company (Ganga Traders).
The distributor's code comes from the bill numbers that person sends (GT/1187 gives GT), or from the
company's initials. This mapping is saved, so next week uses the same codes.

**Attachments.** We decide what a file is from its content, not its name, because real exports
are named like `IMG-20261009-WA0012.jpg`.

- Photos go to Muse Spark. Without a key, Tesseract OCR reads them and our own parser picks out bill
  rows by finding three numbers on a line where quantity × rate = amount.
- PDFs are read with pdfplumber (tables first, then text), with Muse Spark as a backup, and scanned
  PDFs get turned into images.
- Voice notes go to Muse Voice Transcribe, with local Whisper as a backup.
- When OCR misreads a bill number (GT/1187 as G1/1187), we fix it using the chat message the photo
  came with. Messy item names get matched to products the distributor already sells.

**Understanding messages.** Each message or transcript gets turned into facts: schemes, rates
someone quoted, credit terms, "I've paid", deliveries. Our own rules cover the common ways people
say these things ("20 carton lo, 2 free milega", "10 pe 1", "बीस कार्टन पर दो फ्री",
"do carton free denge agar das carton loge", "hamesha 10+1", "is mahine 5% discount",
"45 din ka credit, 2% mahina byaj"). Hindi number words only count as numbers when a unit follows,
so "bhej do" is never read as "send 2". With a key, Muse Spark reads the message as well.

Everything we learn is saved with where it came from (file, chat line, bill row, sender) and when it
arrived in the chat. Reading the same week twice doesn't create duplicates.

## Why answers change at the right time

A report for a given date only looks at what had arrived by the end of that day. That one rule
handles most of the tricky cases:

- **Which rate applies.** Out of the rate lists that cover the bill date, the one that arrived most
  recently wins. So a corrected list sent on Thursday replaces Monday's. A list sent on 9 Dec that
  says "3 Dec se lagu" re-prices bills from 3 Dec onwards, but a bill dated 2 Dec stays on the old
  rate. Run the report as of a date before that list arrived and you get the old answer. Two lists
  for the same date that disagree, with neither marked as a correction, are a conflict.
- **Quoted rates.** If a salesman quotes a rate after the rate list and it doesn't match, that bill
  becomes a conflict for the owner rather than a claim.
- **Payments.** A UPI screenshot is linked to a bill by the bill number in the message sent with it
  (or the message just before), or failing that by a unique amount match after the bill date. A
  screenshot forwarded twice only counts once.
- **Credit terms.** The owner's word beats a contract card, which beats what the distributor said in
  chat, which beats the default of 30 days at 18% a year.

Since every answer depends only on dated records, the order of files in a folder never changes the
result. We test this by rebuilding a week in the other export format, split across two chat files,
with renamed attachments.

## The six checks

- **Rate mismatch:** the billed rate (after any line discount) is more than ₹0.50 above the rate
  valid on the bill date. Amount = (billed − agreed) × quantity, before GST.
- **Duplicate bill:** same distributor, same items and quantities (names matched loosely, rates
  can differ), and the same delivery: the same challan number, or delivery dates within 2 days. A
  copy billed weeks later is caught through the delivery date printed on it. A later bill with its own
  later delivery is just a re-order. Amount = the full value of the repeat bill.
- **Scheme not given:** a scheme from the rate list, a named salesman (in chat or a voice note) or
  the owner, and a bill on or after that date that qualifies. Free goods already on the bill (a free
  row, a free-quantity column, or a price that already includes them) are subtracted. Amount = missing
  free units × the rate valid on the bill date, or the missing discount.
- **Paid but shown due:** the latest statement still lists a bill as due even though a payment made
  before the statement covers it. Amount = the payment.
- **GST error:** more tax was charged than the correct rate on the right base (after discounts; free
  goods aren't taxed). The correct rate comes from the HSN table (`harness/data/gst_rates.json`), or
  the rate list's GST column for items not in the table. Amount = tax charged − tax due.
- **Credit-period risk:** an unpaid or part-paid bill whose due date falls within the next 7 days,
  including bills we only know about from a statement. Amount = outstanding × annual rate / 365 ×
  days from the due date to the end of that 7-day window (at least one day).

**One-time schemes.** A scheme only applies once unless the message says otherwise ("hamesha",
"har order", "every order", "standing", "jab bhi"). "Is mahine" makes it valid until the end of
the month. A one-time scheme is used up by the first qualifying bill after it was offered, whether
or not the free goods were actually given, so we never claim it again on the next order. "X pe Y
free" scales with the quantity; "X lo, Y free milega" means Y once. If the same person makes a new
offer it replaces their old one. If two different trusted sources disagree, it's a conflict.

**Who we trust**, following the glossary: signed rate list, then the owner, then a named salesman,
then anyone else we can identify, then unknown numbers, then forwarded messages. Forwarded messages
and unknown senders can't create schemes, rates or payments.

## Conflicts and missing documents

A **conflict** is when two trusted sources disagree on something the answer depends on: two rate
lists for the same date, a rate list against a salesman's quote, two different schemes. We show both
sides and the money at stake, and leave it to the owner. Khata never picks a side.

**Cannot determine** is for when we'd need a document we don't have. We say what's missing and who
to ask: the distributor for a rate list or HSN codes (with a drafted message), the salesman if a
scheme didn't say which product, or the owner if the chat says "paid" but there's no screenshot. A
bill that charges no GST, or charges less than the list, isn't treated as a question.

## What Khata does in each mode

- **Confirmed problem:** in supervised mode, it drafts a WhatsApp reply for the owner. In
  autonomous mode, it sends the reply itself only if all of these hold: the evidence is complete
  (real documents, not just a voice note), nothing on that bill conflicts, the amount is under
  ₹2,000, it's just a query, and confidence is at least 0.75. Otherwise it drafts and waits, and
  says which check failed.
- **Credit-period risk:** always just a reminder to the owner.
- **Conflict:** always goes to the owner.
- **Cannot determine:** a drafted request to whoever has the document, or a question for the owner.

Every draft is a short, polite Hinglish message. There's no payment action anywhere in the code,
and drafts are cleaned of anything like a PIN, OTP, account number or UPI ID.

**Scam messages.** Every message, transcript and document is checked by rules (English, Hinglish
and Devanagari), with Muse Spark as a second check on forwarded messages and unknown senders.
Anything flagged is set aside: it creates no records, never shows up as a finding, and is listed in
`safety_alerts`. When we send chat or OCR text to the model, it's clearly marked as data, not
instructions.

**Not overloading the owner.** At most 60% of findings go to the owner. Conflicts always do. If
open questions would make up more than half the report, we keep one question per bill, then combine
requests for the same document from the same distributor (one rate list answers all of them), and
only as a last resort move the least important ones to `pending_requests`. Very small reports are
left alone.

## What the owner sees

Next to `report.json` we write `report.html`, a single page that works offline on a phone: totals,
money per distributor, each problem with its proof and a copyable WhatsApp draft, blocked scam
messages, and open questions. At the top is a short Hinglish message for the owner. We build a plain
version from the report, then ask Muse Spark to make it read naturally, and we only use Muse's
version if every amount and bill number in it appears in the report and it never asks for a PIN.
`check <folder>` runs ingest, report and the page in one step for any new export.

## Confidence

Confidence is our estimate that both the verdict and the amount are right. It goes down for each
shaky fact the finding depends on: a blurry or inconsistent bill reading, a less trusted source (and
a voice note more so if the transcription was unsure), a loose product-name match, an effective date
we had to guess, a scheme product we had to infer, a value based on the billed rate because there's
no rate list, a payment matched only by amount, or default credit terms. It goes up when things back
each other up (the owner agreed to the offer in chat) and jumps to at least 0.97 once the owner
confirms it. In practice, rate claims from clean readings come out around 0.95, OCR-based ones
0.81–0.92, and voice-note-only schemes 0.83–0.87.

## Learning from the owner

The owner can answer in structured form or just write a sentence ("Mohan ke saath 150 pe hi deal
hua tha", "Sharma Products ka credit 45 din"). Each answer is saved and used by every later report:

- If they say a finding is wrong, it stays hidden. If they confirm it, its confidence goes up, and
  they can correct the amount.
- If they say a rate was agreed, that rate applies from that bill onwards, so the next bill at that
  price isn't flagged either.
- If they pick a side in a conflict, that settles it.
- If they answer a missing-document question (a rate, an HSN code), the check can now run.
- They can also say a bill was paid in cash, set credit terms, say a salesman isn't allowed to give
  schemes, or say two bills weren't duplicates.

Free text goes through our rules first and then Muse Spark if the rules don't understand it.

## Testing

`make eval` (or `.\run.ps1 eval`) runs 93 tests and then replays our own test shop:

- `test_detectors.py`: each problem type with its look-alikes. For example a bill just before a new
  rate list (fine) vs just after (wrong), a re-order vs a duplicate, one-time vs permanent schemes, a
  statement made before the payment, a bill with no GST.
- `test_level3.py`: the traps the problem statement warns about. Two weeks in separate runs with a
  backdated rate list, a scheme meant only once, a forwarded "pay ₹50,000" message, a conflict settled
  by feedback, autonomous mode's safety rules, the 60% escalation cap, file order not mattering,
  re-running the same week, and a brand-new shop.
- `test_media.py`: real rendered photos (one sideways, tilted and blurred), a real PDF, a UPI
  screenshot and a statement, read with no saved `.json` files.
- `test_llm_paths.py` and `test_muse_api.py`: the model code checked against a scripted fake model
  and a fake Meta server, since tests shouldn't spend credit.
- `test_owner_view.py`: the summary and web page, including a fake Muse that tries to slip in a
  made-up amount (rejected).
- `test_datasets.py`: practice, exam, and the two-week test shop in `evals/scenarios/annapurna`
  (a new shop, feedback between the weeks, and an answer key covering every trap above).

Our grader (`grader/grader.py`) is stricter than the one we were given. A problem only counts if
the bill, type and amount all match (within ₹1 or 1%). Evidence has to point at a real file or chat
line, wrong claims cost double, and the five score-capping mistakes are all checked.

Results: practice 100/100, our test shop 100/100, exam rate ₹1,000 / duplicate ₹12,000 / scheme ₹780 /
paid-but-due ₹8,000 / GST ₹1,300, with three Banaras Wholesale bills marked cannot_determine. Run on
real files only, Muse read all the test-shop photos correctly. Our generated voice note uses a
robotic text-to-speech voice, and the transcription lost the numbers in it, so that one scheme was
missed. A real recording fixes it.

## Limits and what we'd do next

- **Voice notes are the weak spot.** Mumbled Hinglish numbers are hard for any transcriber. Next we'd
  pass the distributor's product names as transcription hints and let Muse Spark fix the transcript
  against what that distributor actually sells.
- **The reference files may not be the official ones.** The glossary, data and grader we started
  with came from Gemini, not the organisers. GST rates are in `harness/data/gst_rates.json` and the
  limits in `harness/config.py`, so the official numbers can be dropped in without touching code. The
  credit-interest formula (days from the due date to the end of the 7-day window) is our reading of
  "interest that would be due", and it's one line to change.
- **Units.** We compare rates when the units match or aren't printed, and ask when they clearly don't
  (carton vs piece). A per-product conversion table learned from past bills would be better.
- **Duplicates with no delivery date.** If a repeat bill comes weeks later with no delivery date or
  challan number, we assume it's a re-order. We'd rather miss a claim than claim twice. Matching
  "delivery ho gaya" messages to bills would close this gap.
- **Confidence is hand-tuned.** With more labelled weeks we'd fit it to what owners actually confirm.
- **Product ideas:** read WhatsApp Business messages live instead of exports, track credit notes
  after a claim, and send the owner a short Hinglish voice summary.
